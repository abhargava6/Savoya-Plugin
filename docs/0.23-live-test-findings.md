# Live MCP test — findings

Run 7 Oct 2026 against the acceptance MCP, profile **201890 (Ayush TC / Yerdle)**,
Irvine two-transfer request, 2027-03-20. Raw responses from `resolve_itinerary_stops`,
`preview_rate_batch`, `generate_quote_options` ×2 and `calculate_quote_units` ×2.

Closes **Q4** and **Q5**, confirms **B1**, **D1** and capacity-aware quantity, and turns
up five things no one had asked about.

---

## Q4 — `strategy` is a label, not a selection input

**Answered: it changes nothing in Core's math.**

Method: Core rejects duplicate options outright —

> *"This comparison alternative duplicates options[0]. Use distinct vehicle choices;
> labels alone do not create an alternative."*

— so strategy can't be isolated with identical units. Instead the same two distinct
options were run twice with only the strategy strings swapped.

| | Run 1 | Run 2 |
|---|---|---|
| opt_a strategy | `value` | `cost_saving` |
| opt_a total | **$693.00** | **$693.00** |
| opt_b strategy | `elevated` | `quality_focused` |
| opt_b total | **$4,019.40** | **$4,019.40** |

Identical totals, identical vehicles, identical quantities, identical rate ids. The string
appears only in `presentation.data.scenarios[].strategy`.

**Selection is driven entirely by the vehicle argument**: `vehicle_type_ids` (candidate
list → Core prices each, picks lowest successful total) versus `vehicle_type_id` (fixed).

**Consequence for B4:** unblocked, and use `strategy` as an honest label for what the
option *is*. Do not expect Core to interpret it, and do not pick a strategy hoping for a
different answer.

## Q5 — a temporary **transfer** rate will not price a multi-stop leg

**Answered: blocked. `hourly` is the only option for a waiting leg.**

Sent: 3 stops (hotel → venue, 2h wait → hotel), SUV, `temporary_rate: {rate_type:
"transfer", amount: 20000}`. Core returned:

```json
{"status":"blocked","error_type":"quote_units_unavailable","core_status":422,
 "client_error":{"code":"quote_units_unavailable","category":"availability",
   "user_message":"One or more trips could not be priced with the selected vehicles and rates.",
   "recovery":{"code":"review_rates",
     "message":"Please choose another vehicle, provide a temporary rate, or remove the unavailable option."}}}
```

The engineer's handoff asserted "transfer rates need exactly two stops." **Confirmed
empirically**, and it holds for temporary rates too.

**Consequence:** our under-3-hour rule produces exactly this shape routinely. When such a
leg has no stored rate, the CSM must be asked for an **hourly** rate — never a transfer
one. That belongs in the decision tree as a rule, not a surprise.

## D1 — the greeter prices through Core, and the hand-entered figure was 3× too high

`calculate_quote_units` with `vehicle_type_id: 12`:

| | |
|---|---|
| Rate id | 55549, `HourlyRate` |
| Rack rate | **$100.00/hr** |
| Effective rate | **$76.99/hr** (30% discount + 10% fuel) |
| Minimum | 2 hours |
| Total | **$153.98** |
| Cancellation | 2 hours |

For comparison, the Irvine quote that went to a client carried a hand-entered
**"On-site coordinator — 4 hrs at $235/hr = $940"**. Core's actual effective rate is
$76.99/hr. Even at four hours that is ~$308.

**This is the strongest argument in the register for D1.** It isn't tidiness — a CSM
guessed a number roughly three times Core's rate and it reached a client.

**Two modelling details that still need working out:**

1. **Duration didn't take.** `duration: 4` on the final dropoff was ignored —
   `billable_hours` came back as 2, the minimum. `duration` applies to intermediate and
   as-directed stops, so a 4-hour greeter needs an as-directed structure, not a duration
   on the dropoff.
2. **The stop shape is semantically wrong.** Priced hotel → venue, it reported a
   13-minute drive time for someone standing in a lobby. The right shape is probably
   hotel pickup + as-directed with a duration. Needs design before D1 is built.

## B1 — passenger omission confirmed working

Every unit priced with no `passenger_id`:

```
"passenger_selection_source": "quote_only_fallback"
"warnings": ["No passenger was selected. Savoya attached an eligible passenger only
             to calculate this unsaved quote; the passenger selection was not saved"]
```

Exactly as the schema documents. **Open UX question:** that warning appears on every unit,
every option and the aggregate. Showing it to a CSM each time would be noise, and it is
arguably not their problem — but suppressing a Core warning wholesale is the habit that
hides real ones. Needs a decision in Group C's review.

## Five things nobody asked about

### 1. `vehicle_options[]` — every candidate comes back priced
Each quote unit returns **all** candidates it evaluated, each with its own
`unit_total`, `quantity`, `line_total`, `rate_id` and full `pricing_summary` — not just
the winner. The plugin currently models one rate per leg and throws this away.

That is a free per-leg comparison we are discarding, and it is close in shape to what
GREEN-371 will need for per-source line items (**E1**). Worth designing `quote.json`
around deliberately rather than discovering twice.

### 2. A `presentation` block the plugin ignores entirely
Every response now carries `presentation` with a `view` (`rate_preview`,
`scenario_comparison`, `quote_result`, `blocked`), a `title`, pre-formatted rows, and
`actions` carrying intents like `select_scenario` and `refine_quote`.

The MCP is proposing a UI. We render our own and ignore it. Not necessarily wrong — our
document layer is the product — but it is a deliberate choice nobody has made yet, and
the `actions`/`intents` may be the intended way to drive the refine loop.

### 3. The blocked-response shape — which is Q1's answer
The Q5 failure returned the shape A1 needs: `status: "blocked"`, a typed `error_type`, a
`client_error` with `category` and a CSM-ready `user_message`, and a `recovery` block with
an actionable next step. `presentation.view: "blocked"`.

**A1's replacement flow should surface this verbatim** rather than inventing wording.
It is also the natural blocked fixture for the test matrix.

### 4. Greeters are absent from `preview_rate_batch`
The rate preview's `vehicle_rate_evaluations` lists Sedan, Premium Sedan, SUV, Exec Van,
Sprinter, Mini Bus, Coach Bus — **no greeter types**, and `missing_vehicle_type_ids: []`,
so Core does not consider them missing. `vehicle_scope: {"kind":"market"}` appears to
cover capacity-bearing vehicles only.

**This breaks the greeter rate check as designed in D1.** The four-way rule assumed we
could ask the market whether a greeter rate exists. We cannot, via rate preview — but we
*can* price one directly with `calculate_quote_units`, which succeeded. So the check
becomes "attempt to price it; a blocked response means no rate," which is a different and
slightly heavier flow. **D1 needs amending before it's built.**

### 5. Odds and ends
- **Exec Van** is capacity **14** (confirming B2's correction from our "~10") and has
  *no* hourly or transfer rate in Orange County — `hourly_rate_not_found`,
  `transfer_rate_not_found`. Our table's "often unrated" note was right.
- **Coach Bus**: no rates in this market either. Both buses are `client_can_book: false`.
- **Sedan transfer** is a `CompanyTransferRate` of **$770.00** against an hourly of
  $136.29 — a Yerdle-specific rate that looks anomalous and is worth someone eyeballing.
- `requested_stop_count` was accepted everywhere without complaint (**B3** is safe).
- New `adjustments` fields on every unit: `special_handling_basis_points`,
  `temporary_rate_used`.
- Core rejects duplicate comparison options — a server-side guard against fake
  comparisons, which our "every option must contain every trip" rule now has backup from.
