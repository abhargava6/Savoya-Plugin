Scoping MCP traffic at Core: the recommended fix

Core cannot tell an MCP call from a web-app call today. Both arrive as an Auth0 token for the same Core API audience, and Core looks up the user from sub without checking which Auth0 client the token was issued to. Since 20 Oct the MCP sends the attribution headers Core already logs for its mobile apps (App-Name: savoya-mcp, App-Version, Device-Brand: AI Tool, Device-Name set to the AI tool from the verified token), so MCP traffic is now visible by app and AI tool in Core's request logs. The headers are recorded, not checked. The exposure is narrow while the token stays inside the MCP server, but the defence should not depend on that.
Proposed: Core reads the client identifier carried in the exchanged token (the OBO client's id) and, for that client only, allows the /api/v1/quote_builder/* routes and nothing else. Two ways to do it: a separate Core API audience for MCP traffic, or an allow-list keyed on the token's client claim. Either makes the scope a Core rule rather than a property of the MCP's code, and it scales: each new MCP capability adds its routes to that list explicitly. The exact claim name needs confirming against a real exchanged token.

Phase 1, agreed by Ayush and Ethan. The MCP keeps consuming the current API response unchanged and, before returning it to the chat, converts client name, email and phone into a clickable link that opens the client's profile page in the Savoya web app. The user still gets to the client in one click; the account details stay out of the conversation. Phase 2, when the MCP's capabilities expand: the API returns only ids where client information is asked for. That decision waits on Savoya's AI governance policy, which is still being defined.
Three details to settle while building phase 1. The link's visible text must not be the name or email, or the data still reaches the model; use a fixed label such as "Open client profile". The quote document prints "Prepared for" the client, which the plugin currently takes from the resolved client, so the document flow needs the name from the user or the request instead. What the user types is not filtered: searching for a client by email puts that email in the chat whatever the response contains.
Logs. The MCP logs at info by default, which records timing and routing only. Quote payloads and Core error previews appear only at debug, which should stay off in production. Core keeps its detailed diagnostics in its own logs and returns codes to the caller.

When more APIs are exposed through the MCP

The server is built to take a second capability without reshaping. Each capability is a domain with its own tools, schemas and Core client; authentication, rate limiting and logging are shared. Three rules carry over to every new domain. Every tool must state whether it writes; it will not compile otherwise, so a future booking tool cannot inherit "read-only". Each domain gets its own dedicated Core endpoints behind the same role check and flag, never a reused web-app controller. Write tools are not built yet, deliberately: they need an idempotency key so a retry cannot double-book, and a prepare-then-confirm step so the user approves a payload Core issued rather than one the model composed. To add before the first new domain ships: the Core-side route allow-list above, a per-domain flag, and a review of each new response against the PII rule.

The three dashed boxes are the only third-party dependency, and they are community demo services. route_map.py alone uses them, for a street basemap and a road-shaped line. The engine already supplies drive times — the router's own minutes are explicitly discarded in favour of Core's — so nothing that affects a quote comes from here. Corporate networks block them routinely; the map then falls back to a basemap-free overview drawn from coordinates the engine resolved, titled differently and labelled as not showing driving routes.
Why this shape. The plugin implements no pricing arithmetic of its own — every number traces to a Core call, and that includes the discount, the fuel surcharge, vehicle quantity, billable hours and each option's total. The two-skill split exists because the jobs have different audiences: intake's only output is a number the CSM can act on, while the document flow's questions are about presentation. A quote answered in chat with no document is a complete, cheap end state.
The tool contract is a file, and it is enforced. mcp-contract.md holds a fenced tools block that is the contract, plus a tools-removed block recording what left it. A guard walks every .md, .py and .json in both skills and fails on any tool name outside it — matching a pattern for tool-shaped names rather than a list of known-removed tools, so it catches the next removal as well as the last. It raises rather than defaulting if the block is missing: a guard that silently allows everything when its input disappears is worse than no guard, because it still prints a tick.

The plugin's contract block, the MCP server's tool registry and the MCP's Core client agree on these twelve names, and the nine Core paths the MCP calls are exactly the nine routes the Core branch adds. There is no tool without a route and no route without a tool.
Two tools were removed, and with them the whole idea of an estimate. plan_approximate_quote_units and calculate_quote_options are gone from the server, recorded in the contract's tools-removed block, and forbidden anywhere else in the tree. The plugin now has no approximate path at all — the approximate one priced differently from the web app, which is why it went. What replaced it is not an estimate but a question: a profile with no passenger prices normally, and a market with no stored rate means asking the user for a temporary base rate and re-quoting through Core. "No rate available" is a question to the user, never an estimate.
A supplied rate is a base rate, and that has to be said while asking. $250.00/hr supplied became $192.50/hr effective after a 30% contracted discount and 10% fuel. A CSM who enters a partner's cost quotes the client about 23% below it, and the moment of asking is the only point where that is catchable — afterwards it looks like an ordinary price.

Four corollaries, each found later and each now guarded

A document line moves what C4 compares; it does not switch C4 off. The check originally ran only when no document line had been added, on the reasoning that the total is then deliberately no longer the engine's — true of the total, not of the engine's share of it. One flat $200 coordinator line disabled the only fail-closed money check in the plugin, on a quote also built from a hand-transcribed engine response. Reproduced: a $100 slip in one leg's line total ships a client document $100 light, silently.
A waived engine line has to be added back before comparing. Core's aggregate still contains it, so the document total is legitimately short by exactly that amount. Nothing added it back, so C4 refused on any waiver — and --waive was unusable for the entire time it was the documented way to drop an engine line. It had no guard on it at all.
Every total is somebody's, and the one with no owner is the one that broke. Option A never computes a percentage; Core never prices an Option B combination as a package, so there was nothing to check it against — and it was the only total still applying percentages itself. It compounded two discounts and came out about 2.3% high on a live quote, overstating the cheaper option and understating the saving being offered.
A reconciling total does not mean a correct breakdown. C4 and C5 guarantee the total by construction, which is exactly why they cannot catch a line mislabelled as its opposite. Reading only discount_basis_points while Core also sent temporary_discount_basis_points leaves the second discount inside Core's net with no line of its own, and the fuel remainder then prints it as a negative "Fuel surcharge" — with the total still exact, so nothing fails.
The same rule governs what the plugin says, not just what it renders. Asked which option is cheapest, it prices the candidates or says a quote is needed. A session did rate-sheet arithmetic instead and told a CSM that sourcing a Mini Bus from Austin would save about $80; the real quote came back $707.18 more expensive, because the arithmetic had missed the positioning drive time that sourcing exists to pay for.

A refusal is a file, and the next skill reads it. When a gate fails (an unresolved stop, a headcount range, a split that does not sum to the headcount per trip), handoff.py writes handoff/blocked.json naming the gate, the reason and the fix. decide.py and normalize_quote.py --from-handoff exit with that message while the file exists. A successful write removes it. The session cannot route around the stop by editing the handoff by hand, and the intake stamps written_by: handoff.py write so a hand-written handoff is visible.
Why reject an older handoff rather than read what you can. A v1 or v2 handoff was written against the previous contract, where an estimate could be approximate, a passenger id was always present, and the sourcing warning arrived on the quote response. Reading those fields as if they still meant that produces a document that looks right. Refusing produces a sentence a CSM can act on.
One field exists only because the document flow cannot get it any other way. sourcing carries the market and excess_drive_time from stop resolution, because the "No local providers" warning naming the market appears only there, while the quote response carries a bare excess_drive_time: true. Without it, a Whistler job billing 12 hours against a requested 8 can only tell the client "a neighbouring market". It is the one piece of state the plugin carries across its own seam purely to cover a Core gap, and closing ENGINEERING.md G4 retires it.
The decisions block drifted, in the one file nothing was checking. It documented a fuel key for three days after the code stopped writing one, and omitted commission_pct and greeter_cost, which had been added. The question-set guard existed the whole time and could not see it: it matched numbered prose lists, and this is a jsonc key block. The file that is the contract between the skills was the one file nothing looked at. The guard now parses that block too, checking the keys and their order against BASE_ORDER.

An inventory check runs before every exact quote, even when the user declined the rate sheet, using the internal display so no rates are shown. It compares the requested vehicle count against the returned market count, deriving the count from passenger count and capacity when the user didn't state one. It is an inventory check, not a driver or vendor schedule check — the counts are static fleet numbers, not date-specific availability.
A lookup is not a choice. The sourcing node presents and stops. The plugin never picks a source market for the user, and never reads a lookup or a rate preview as consent.
Everything is one call where it can be. Stops resolve in one call for every leg; the quote is one call for every unit, mixed-market packages included. That is not only latency — a per-leg loop is how a dropped stop becomes a confident 0-minute drive time, which is why every unit also carries requested_stop_count so Core can tell it was handed fewer stops than were asked for.
Headcount and stops are gated, not just asked. A stop that did not resolve gets a question for the address, never an as-directed stand-in (R83). A passenger range gets a question for the headcount, and the number goes in as passenger_count (R84). When a request splits the group across trips, the counts per trip must add up to the headcount (R91).
Never happens here, by design: covers, personalization, commission, maps, formats. All of that is quote-document's concern. Discounts are the exception that moved — an additional discount is a document-flow question, answered by calling Core again rather than by adjusting the number intake produced.
The presentation block is the only thing the plugin reads. The MCP returns a successful quote as { "presentation": {...} } and nothing else: the compact quote view, presentation version 2, money in cents. quote_view.py is the single reader for both skills, and money is passed through, never computed. It refuses any other version, and says which way to go: a newer version means update the plugin; an older version, or the old raw payload, means the connector is behind and Savoya engineering must serve the compact view (NFR-6). The view stays internal: it carries rate ids, rack-versus-effective rates and limited_availability. The client document is still entirely ours.

A sourced vehicle bills the primary market's rates, not its home market's. Confirmed live: an Austin Mini Bus sourced into Dallas billed Dallas's $314.92/hr, not Austin's $244.09/hr. The nearby market supplies the vehicle, not the price — which makes AC #2 actively hazardous. A nearby market's own rate sheet is not what gets charged when sourcing from it, so it can only be shown with that stated first, and when a sourced quote is in play both numbers must be named.
The returned counts are "additional", not totals. Vehicles whose vendors already serve the reference market are excluded, because they are already counted there. A CSM reading "Market B · SUV 4" will otherwise promise a client four SUVs that may not be four extra ones. The counts are also unconfirmed and promise nothing about fulfilment.
Any service area is sourceable, and a market_ref is scoped to the trip's primary market. The nearby list is a display aid: a market the CSM names is looked up with service_area_ids at any distance. A ref obtained from Austin's lookup is rejected for a Dallas trip with a source_market_ref_mismatch issue. To source into Dallas, look up from Dallas.
A quantity above inventory is Core's to price. After market_inventory_shortfall, a CSM who has the vehicles (a vendor confirmed them by phone) overrides it; the same package goes again with inventory_override: true on the affected units, and Core returns the price with an internal Inventory override warning on each.
Where sourcing lives in the code. It is built in Core's QuoteBuilder as well as on the tool surface: NearbyMarketLookup ranks markets by road distance, SourcingReference signs each market_ref for 24 hours and binds it to the user and the market the lookup started from, and MarketInventoryCheck refuses to price more vehicles than the chosen markets hold (market_inventory_shortfall), unless the unit is marked inventory_override; then it prices and attaches a warning naming the shortfall. One itinerary may draw on up to seven markets. An expired ref returns sourcing_reference_expired naming the market, so the plugin can look it up again. The sourced vehicle is priced by re-running the web app's own service-area override (QuoteUpdateStrategy.requote), which is why it bills the primary market's rate.
The schema extension the design predicted was not needed. The earlier design expected a sources[] array under each leg's pricing. In practice each allocation is already its own quote unit, so the existing per-leg structure carries it with only sourcing flags added. A stop in no service area at all turned out to be a real, separate case — and it broke the feature's own verifier, which rejected a sourced leg whose market matched its primary market. That is correct for an override and false by construction here, where Core reports one market as both. The real Sicily legs of a live quote failed verification.

This page previously drew the capture as one arrow to Drive, and that simplification hid the problem. Five decisions here each came from a specific loss. Two real captures — 192 KB and 36 KB — were written to ~, reported as saved, and lost, because ~ is a cloud container on claude.ai and an isolated VM on a linked desktop; only a connected folder is really the user's disk. The old rule kept anything over 25 KB local, so the richest sessions were exactly the ones that never arrived. Holding the full capture until after the feedback exchange made the richest artifact depend on a conversational step, and on a live quote that step was skipped. A failed upload used to mention rather than ask, and three sessions in a row ended with the record stranded. And a malformed call printed argparse usage to stderr — a bug report that never happened, since the step is specified as silent.
--workaround is the field that matters most. A session that patched a script in a working copy or rebuilt a line by hand is the most valuable one of the week and the most likely to skip the step. The highest-risk workaround found this way is the hand-transcribed engine response: five sessions re-typed a quote response too large to save, which defeats C4, because both sides of its comparison then come from the same typing. That is ENGINEERING.md G6, and it is why the compact response mode is a correctness item rather than a convenience.
A blocked session leaves a record too, and the files in it are the real ones. A refusal writes a packed .blocked.json.gz.b64 envelope carrying the refusal, and the capture lists each upload with its size and sha256 and says to upload it exactly as written (R94). unpack_capture.py warns when a checksum does not match.
Replay is the most productive test in the system. Eleven defects came out of three live quotes, found by replaying the captures through the build rather than by reading the session notes — and two of the eleven had been introduced by the previous day's fixes and were invisible any other way. The notes say what a session reported; the capture is what it actually sent and received.

Six things have to be true on a CSM's machine. Five of them can be false without anybody noticing, which is how the plugin ran for weeks with nothing reaching the capture folder.

Two copies of the plugin is a silent fork, and it is the newest entry here. Every older copy stays on disk, which makes the un-suffixed directory permanently the first one ever installed — so a glob on the plain name matches it and nothing else. The skills themselves loaded from the current copy, so the flow looked right and the duplicate was invisible. The damage was narrower and worse for being quiet: a session that located a script by name ran September's, whose capture_session.py has no --auto flag, so the call was rejected with bare argparse usage and the session recorded nothing. Both skills now match savoya-quoting* and take the highest version numerically — as strings, "0.9" sorts above "0.25", and this repo has passed through both.
The setup check is the only thing that closes this. It runs in two halves because neither can see the other's world: a local script reports identity, which copy is in use, the capture folder, the backlog and what the map can do here; the session then calls the connectors rather than assuming them — including writing a small test entry to the shared folder, since Editor access and view-only look identical until something tries to write. That entry is left in place deliberately, so the folder's owner can see whose setup is verified. Reachable by the words a CSM would actually use: "check my quoting setup", "is this saving?", "why isn't anything showing up?"
preflight.py is a different thing and does not help here — it checks local Python packages for PDF, verification and maps, and never touches a connector, the folder, or identity. Neither ever shows a CSM an install command: the only technical instruction a CSM receives is Print → Save as PDF, worded for their operating system.
