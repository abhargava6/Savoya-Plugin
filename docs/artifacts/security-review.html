What is new

What is new in Core and the MCP

Two pieces of new code talk to each other: a new MCP server, and a set of new quote-builder endpoints in Core. The endpoints reuse Core's existing reservation and pricing engine, so a quote from Claude is calculated exactly as the web app calculates it.

Security

How security is implemented

There is no shared service account anywhere. Every request carries the identity of the Savoya employee using Claude, and Savoya Core makes every access decision with the same user record and roles it uses for the web app.

High-level architecture. The plugin guides Claude through Savoya's quoting workflow; the MCP server exposes the tools; Core owns the data, permissions and prices.

Checks at each layer

LayerWhat it checks
Auth0Only approved AI clients can connect (Claude and ChatGPT, each imported by name); open self-registration is turned off. The user signs in with their normal Savoya login and approves one permission, access:savoya_mcp
MCP server, on entryThe token's signature, issuer, audience, expiry and permission on every request. Machine tokens are refused. Requests to unknown hosts and bodies over 1 MB are rejected
MCP server, per toolInputs validated against each tool's schema before Core is called. Per-user rate and concurrency limits
MCP server to CoreA short-lived Core token for the same user, obtained by Auth0's on-behalf-of exchange. Kept in memory only, never logged. If the exchange fails, the call stops
Core, on entryEnabled user, an allowed role (admin, manager, sales agent or Groundwork manager; every other role is refused), and the enable_quote_builder_api flag, which switches the endpoints off for everyone
Core, per requestWork ceilings on every request, and quotes calculated without saving anything
MCP server, on the way backEvery Core response checked against the agreed contract before Claude sees it. A response that does not match is blocked, with no price shown

Authentication

How authentication works

The user signs in once. After that, each tool call carries a token that only works against the MCP server, which swaps it for a Core token naming the same person.

No secrets on the AI sideClaude signs in with a public identity and a one-time proof (PKCE). The only client secret is the MCP server's, held in its secret manager

Rate limiting

How we are rate limiting

The limits are a safeguard against someone, or a runaway agent, flooding the system. They sit well above real use, so they protect Core without slowing anyone down.

WhereLimitSetting
MCP server, per userTool calls per minute60
Burst20
Calls in progress at once, per user4
Calls in progress at once, per server100
MCP server, per requestOptions in one comparison5
Stops in one itinerary25

Vehicle evaluations in one rate preview or batch40

Nearby markets shown for one trip, across pages12

A call over the MCP limit is refused with HTTP 429 and a retry time, before it reaches Core. The 1,000-a-minute limit is Core's existing protection for its whole API and applies to this traffic like any other.

Tool calls and Core calls

One tool call is one Core API call, with one exception: a comparison (generate_quote_options) makes one call per option, so two to five. A rate-sheet batch that is too large for one request can be split into a few smaller ones.

What real use looks like

A complete quote takes about seven tool calls. At beta scale, ten people making two quotes a day each, that is roughly 140 tool calls a day across everyone, against a limit of 60 a minute for each person. Quote calculations already run through the same Core engine the web app uses for every quote today, so this traffic does not change Core's performance.

Traffic from the MCP

Is MCP traffic scoped at Core?

Can we tell traffic coming from the MCP apart from traffic coming from the web app or anywhere else, and see its volume?

Yes. The MCP server calls only the nine quote-builder endpoints, and all nine are new. Nothing else in Savoya uses them, so MCP traffic is separate by endpoint.

  • Visible in New Relic as its own traffic. Volume, latency and errors for /api/v1/quote_builder/* are the MCP's, with no web-app traffic mixed in. An issue on one of these endpoints can be investigated without separating it from anything else.
  • Labelled on every call. The MCP server sends the same attribution headers Core already records for its mobile apps: App-Name: savoya-mcp, App-Version, Device-Brand: AI Tool, and Device-Name set to the AI tool (Claude, Claude Code or ChatGPT), taken from the verified token. Core's existing request logging stores them with each request, so MCP traffic can be filtered by app and by AI tool. Every response and error also carries a request id that links the MCP's log to Core's.
  • No existing endpoint is involved. The MCP does not call any endpoint the web app uses, so it cannot add load to them.
  • Same authentication as the rest of Core. Calling these endpoints directly would need a valid token for an enabled internal user with an allowed role, and would return nothing that user cannot already see by logging in to Savoya.

Personal data

Is anything preventing PII reaching the LLM?

The tools show internal users the client details they need to quote, the same details they see in the Savoya web app. The users are internal Savoya staff, and the data stays within their own Claude session.

What reaches Claude, and what does not

DataReaches Claude?
Client name, email and companyYes, to confirm the right client
Passenger name and emailYes, when the user names a passenger
Pickup and drop-off addressesYes, to confirm the trip
Rates and quote totalsYes; the purpose of the tools
Payment details, card dataNo. No tool returns them
Tokens, secrets, login codesNo. Never in a tool result, and removed from logs

The MCP server stores no business data or conversation history. By default its logs record timing and routing only; quote contents are logged only when debug logging is switched on for troubleshooting.

Why this is the right position for now

Staff already use AI at Savoya in a far less controlled way. Browser automation, where an AI tool drives the web app on someone's behalf, can see every screen the user can, including all client details. Even its makers ship it as a beta with repeated warnings. The MCP gives the AI a narrow, read-only, logged path that returns only what quoting needs, so it reduces the exposure that exists today.

Filtering client details out of the MCP would not stop that data reaching AI tools while browser automation and personal Claude accounts on company devices are still possible. Doing it well needs those controls first: an enterprise plan with AI browser use disabled and personal accounts blocked.

Proposed policy: client details may be shown in the chat to internal users until those controls are in place. A filter that keeps client details out of the conversation has been designed and can be built when the policy calls for it. To be confirmed with Mike and Mark.

Future APIs

When more APIs are exposed through the MCP

Every new capability follows the same pattern as quoting, so the answers on this page carry over.

  • Dedicated endpoints. Each capability gets its own Core endpoints, behind the same login, role check and feature flag. Existing web-app endpoints are never exposed directly.
  • Shared protections. Sign-in, token exchange, rate limiting, logging and response checks are part of the MCP server itself, so a new capability gets them without extra work.
  • Writes are declared. Every tool must state whether it changes data. Any tool that would book or change something is designed separately, with the user confirming exactly what Core will do before it happens.
  • Data reviewed per capability. What each new response returns is decided when its endpoint is designed, under the AI data policy in force at the time.
